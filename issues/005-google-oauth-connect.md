# M2: Build the Google OAuth connect flow with encrypted token storage

## Context
Depends on 003: Gmail REST MailSource adapter and 004: worker/ entry.
Read first: docs/oauth-and-verification.md (Option B — BYO Google Cloud
client), ADR-0008 ("The Worker holds Google credentials" — AES-GCM, key only
in Worker secrets, ciphertext in D1, "a D1 export alone is useless"),
ADR-0007 (opt-in writes; `gmail.modify` is a separate consent), CONTEXT.md
(Account, Read-only by default).

This gives 003's injected `tokenProvider` a real implementation and gives 006
credentials for cron sync.

## Decision
The Worker runs the OAuth flow itself against the operator's own Google Cloud
OAuth client (BYO — no CASA exposure for the project).

- Config/secrets (wrangler): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
  `TOKEN_ENC_KEY` (32-byte base64, generated by the operator; used as the
  AES-GCM key via WebCrypto `crypto.subtle`).
- New D1 table via a forward-only migration in `src/index/migrations.ts`
  (the next schema version — coordinate with 006; whichever lands first takes
  the next number) — harmless locally (empty table): `google_tokens`
  (`account` TEXT PK — the operator label per CONTEXT.md "Account",
  `address` TEXT, `scopes` TEXT, `refresh_token_ciphertext` BLOB, `iv` BLOB,
  `created_at`, `updated_at`). Plaintext refresh tokens never touch D1 or
  logs; access tokens live only in memory per invocation.
- Setup pages served by the Worker (simple server-rendered HTML, no
  framework): `GET /setup` lists connected accounts + "connect account";
  `GET /setup/google/start?account=<label>&writes=0|1` → Google consent
  redirect (`access_type=offline`, `prompt=consent`);
  `GET /setup/google/callback` → code exchange, encrypt + upsert row,
  confirm page. Gating: `/setup` pages accept the 004 dev bearer as a
  `?token=` query param (browsers can't send Authorization headers);
  `/setup/google/callback` is exempt from the bearer check and validated
  instead by the signed `state` parameter minted when the flow started
  (later 007 session).
- `redirect_uri` is derived from the Worker's public origin (request URL);
  the operator must register that exact URI on the BYO Google client — call
  this out in the setup page.
- Scopes: default `gmail.readonly`. **Separate opt-in re-consent path** for
  `gmail.modify` (`writes=1` — the `mail-index setup --enable-writes`
  equivalent per ADR-0007): a distinct consent round-trip that replaces the
  stored grant; `scopes` column records what was granted so 008 can gate
  write tools.
- Multi-account: one row per account label; `check()` via the gmail-rest
  adapter verifies identity (address) after connect.
- Token provider implementation (worker-side module): decrypt refresh token,
  exchange for an access token at Google's token endpoint via the same
  injectable-fetch discipline, cache in memory until expiry, plug into the
  003 adapter's `tokenProvider`.

## Acceptance criteria
- [ ] Migration to the next schema version adds `google_tokens`; local `mail-index` runs
      it as a no-op-content migration and all existing tests stay green
      (`SCHEMA_VERSION` bumped, migration test updated).
- [ ] Full connect round-trip works under `wrangler dev` against a fake
      Google endpoint in tests: start → callback → encrypted row in D1 →
      adapter `check()` returns `ok:true` with the fixture address.
- [ ] Stored ciphertext is not decryptable without `TOKEN_ENC_KEY` (test:
      decrypt with wrong key fails); no plaintext refresh token in D1, logs,
      or error messages (assert on the persisted row + thrown errors).
- [ ] Readonly connect yields a grant whose `modify` attempt surfaces the
      typed insufficient-scope error; the `writes=1` re-consent path updates
      `scopes` to include `gmail.modify`.
- [ ] Two accounts can be connected and listed independently on `/setup`.
- [ ] Egress guard green: Google token-endpoint fetches live in worker/ or
      the pinned adapter seam, never in guarded `src/` core files.

## Out of scope
- No MCP OAuth / operator login identity — 007 (the setup pages reuse the
  004 bearer until then).
- No cron/queue usage of these tokens (006).
- No write-tool gating logic in MCP tools (008) — only the stored `scopes`
  fact this ticket provides.
- No Google verification/publishing work — BYO client stays in "testing" or
  operator-verified state per oauth-and-verification.md.
